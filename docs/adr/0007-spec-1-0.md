# ADR 0007: Neutral Build Output spec 1.0

Date: 2026-11-09. Status: accepted. The maintainer approved in advance that Claude settles the spec's open decisions for this queue item; every decision below is Claude's call, made on that approval. The maintainer can overturn any of them before the `spec-v1.0.0` tag; after the tag, changing one that existing builds rely on is a 2.0 change.

## Context

`docs/nbo-spec.md` started as a draft (2026-10-22) written before anything was built. Since then the writer, the validator, `nbo serve`, the router, two producers, two provider adapters, the edge and a conformance runner have been built and run, and they disagreed with the draft in many places: capability ids nobody wrote, function fields no producer used, a `variants` file nothing read, a bundle file (`dispatch.json`) outside the digests, a Next.js build that did not give the same content id twice. The open-decisions table at the end of the draft was the last thing blocking a version we can call 1.0. This ADR records how each row was settled, and the rules that make 1.0 stable. The schemas, validator, writer, server and conformance transcripts landed in the commits 52ae80f to 98d026c.

## Decision

The rule for every row: the spec describes what the code does and what the code can keep doing. Where the draft promised more than anything implemented, the promise moves to "Reserved for later" instead of being frozen.

### The open decisions

1. **Regex flavor: RE2 plus `pathNot`.** The JS-only escapes `\C`, `\cX` and `\uXXXX` (and `\u{...}`) are rejected; producers lower lookaheads into `pathNot` or fail naming the pattern. Reason: it is implemented and tested in the router and in validate, and every router family (Envoy, Go, Rust) can run RE2.
2. **Function identity: by name.** URL paths map to functions only in `routes.json`. Reason: it is implemented, and one SSR function serving many routes keeps the number of deployed objects small.
3. **Relation to Vercel's format: not a superset.** An importer for Vercel's Build Output API may come after 1.0. Reason: Vercel's changes should never force an NBO release.
4. **Edge runtime: none in 1.0.** `runtime.kind: "edge"` is reserved; when a minor adds it, the surface is WinterTC APIs plus `node:buffer` and `node:async_hooks`. Reason: no 1.0 target runs one, and Next.js marks its own Edge Runtime as deprecated.
5. **ISR storage: the platform's own cache service (`@nbo/isrcache`).** The same on every cloud. Reason: it is implemented, behaves the same everywhere and survives a move between clouds. Known gap: only `nbo serve` in dev mode wires it today; production ISR is unsupported until a work item gives deploys a cache service and a token (`docs/points-to-improve-or-fix.md` item 17), and the spec says so.
6. **Multi-service apps and daemons: not in 1.x core.** A later extension or 2.0. Reason: Next.js, React SPAs and static sites do not need them.
7. **Manifest shape: split files linked by digest.** Reason: implemented, and a route change does not touch function metadata.
8. **Name and directory: fixed for all of 1.x.** `.nbo/`, `nbo`, `x-nbo-*`, `/_nbo/` and `NBO_` do not change; renaming them is a 2.0 change. Schema ids are `urn:nbo:spec:v1:<file>`. Reason: the product name can change on the surface, but a wire name that changes breaks every stored build.
9. **Extension mechanism: both.** A generic key rule `^x-[a-z0-9]+(-[a-z0-9]+)+$` on five objects (manifest root, `function.json` root, route rule, prerender config, static-index entry), every key declared in `requires.extensions`, plus a typed schema for NBO's own extensions. Reason: third parties get a path without a release, and a misspelled key still fails because undeclared keys fail.
10. **Partial Prefetching: not covered.** Next's client falls back to its ordinary prefetch. Reason: it is a separate client cache and no fixture exercises it.
11. **Packaging: not part of 1.0.** The unit is the `.nbo/` directory. An archive format, signing and provenance stay a sketch after 1.0. Reason: nothing implements them, and the old text promised OCI artifacts and cosign signatures that do not exist.
12. **Unimplemented draft features: reserved.** The 1.0 schemas reject them and a minor may make one core. Reason: no frozen promise without code, and no writer ever produced them, so no stored build breaks.
13. **Framework data requests on prerender routes: core and named as Next's.** `rsc` and `next-router-*` handling (the `vary` header and the cache bypass) is in the spec. Reason: the reference server does it on every prerender route, and it is harmless for other producers.

### The reserved list

Kept for a later minor and rejected by the 1.0 schemas: runtime kinds `edge`, `container`, `python`; `concurrency: "single"`; function fields `group`, `platform`, `placement`, `scaling`, `env`, `bindings`; route actions `transform` and rewrite `url`; match conditions `has` and `missing`; `error` entries other than the 404 file; static `variants`; capability ids `route.middleware` and `cron`; `cleanUrls: false` and `caseSensitive: false`; cron time zones other than UTC; request headers `x-nbo-request-id`, `forwarded` and `x-nbo-geo-*`; packaging, signing and provenance; the control-plane revalidate API; `nbo route test`. Reason for rejecting instead of ignoring: an ignored field is a silent no-op for the person who wrote it. Reason it is safe: git history shows no writer ever wrote any of them.

### Versioning policy

`specVersion` is `"MAJOR.MINOR"`, read from one file (`spec/version.json`) by the writer and the validator. Minor releases only add; anything else is a major. A consumer accepts its own major and any minor not newer than its own, and refuses a newer minor with "upgrade NBO", because core schemas reject unknown fields and an older validator cannot know what a newer field means. Producers write the version they implement. Consumers upgrade before producers. Editorial fixes are patch releases of the document and never change `specVersion` or a schema. Extensions version independently. Reason: this keeps "core schemas reject unknown fields" true across minors without a flag day.

### The determinism rule

The same build input gives the same `.nbo/` and content id. The input includes the source, the producer's settings, the build environment (for Next.js `NBO_BUILD_ID` and `.next/cache`) and the Node major (which sets `runtime.version`). One exception: pages the app itself renders at build time. A Next.js page printing the clock, and Next's own wall-clock stamp in the PPR resume state, differ between builds. Two builds of one commit may differ only in a seed file's digest and size in `static.index.json`, in an entry's `x-nbo-ppr.postponedState`, and in the manifest digests of those two files; everything else must be byte-equal. CI enforces it (`scripts/ci/nbo-diff.mjs --classify`) and also runs `nbo validate --strict` on every fresh build. Reason: the alternatives were to change the fixtures or to hide the difference. Changing the fixtures hides a real property of Next.js apps; hiding the difference in the content id would let two different pages share an id, which breaks the "already live" check, carried files and Speed Insights attribution.

### The `dispatch.json` allowance

`dispatch.json` used to be written after `bundle.index.json`, so it was in no digest and the content id did not cover every byte a function runs. 1.0 lists it in the index. Builds already stored have it outside the index, so validate accepts exactly one unlisted file, `dispatch.json` at a bundle's root, and `--strict` refuses it. Reason: stored builds must keep validating and promoting; a fresh build must not carry the hole. The allowance is dropped in 2.0.

## Consequences

- A function's content id changes for the same commit: the first new build of each project that has functions deploys once, because it no longer matches the live content id. Static and SPA builds are unaffected. Nothing else is forced.
- Rolling NBO back leaves builds a newer NBO made unpromotable on the older one (it refuses a newer minor, and the database is restored from backup anyway). Rebuild them. `docs/production.md` says so.
- Validation is stricter on fresh builds (canonical JSON, references, unlisted bundle files, reserved names, undeclared `x-` keys) and lenient where a stored build could trip it (the `/_nbo/` static key is a warning, `dispatch.json` is accepted). `--strict` is for CI.
- Production ISR is unsupported until a new work item lands; middleware may leak extra `x-nbo-*` response headers. Both are in `docs/points-to-improve-or-fix.md` (item 17) and in the spec.
- The `spec-v1.0.0` tag still needs the maintainer's go-ahead; until then the spec is a release candidate.
- Nothing is decided and left open except the cosmetic product name, which the wire-name rule makes cheap to change.
