NBO Architecture
and API reference
1

How NBO works

NBO deploys the same build to Kubernetes, Cloud Run and AWS Lambda, and moves a project between them as a weighted traffic shift. It is built like a compiler: frameworks write a neutral build output, and cloud adapters deploy from it without knowing the framework.

The pipeline: select a stage

The pieces, by package

Package Role Runs where
@nbo/controlplane The brain: projects, git polling, build queue and runner, setup, transfers, cron scheduler, edge sync. SQLite. Its HTTP API is the only way in. Your server, 127.0.0.1:8081
nbo-server (in @nbo/controlplane, src/server-cli.ts) The operator's command: connect clouds, install the edge, set domains, make API tokens, set up projects. It calls the API over loopback with no token. On the server, docker compose exec nbo nbo-server ...
@nbo/edge The public entry point: maps a host to weighted backends and proxies requests. Your machine, data :9443, admin 127.0.0.1:9444
packages/edge-rs The same edge in Rust (one binary, nbo-edge; ADR 0005). Opt-in until its gate holds; the Node edge is the default. Same ports as @nbo/edge
@nbo/next-adapter Next.js onBuildComplete hook that writes .nbo/. Inside next build
@nbo/producer-static Turns a static folder (or SPA) into .nbo/. Build step
@nbo/writer, @nbo/digest Write the output tree; sha256 over canonical JSON (RFC 8785) for content ids. Build step
@nbo/validate, @nbo/planner Schema + invariant checks; match the app's requirements against an adapter's capabilities. Before every deploy
@nbo/deploy The deploy algorithm and the targets (Kubernetes, Cloud Run, Lambda). Inside the control-plane / CLI
@nbo/adapter-k8s, @nbo/adapter-cloudrun, @nbo/adapter-lambda Images, manifests, kubectl / gcloud / aws calls. Your machine (shells out)
@nbo/cli nbo validate | plan | serve | deploy | conformance. Also the server baked into every app image. Your shell, and every app container
@nbo/serve, @nbo/router The runtime that serves .nbo/: six-phase RE2 router, static files, prerender/ISR. Every app container
@nbo/funcproxy, @nbo/nodehost Call functions (local spawn, in-cluster URL, Cloud Run with an ID token, or a Lambda function URL signed with SigV4); Node ↔ Fetch bridge. App containers, function containers
@nbo/isrcache ISR cache service (in-memory, byte-limited, /healthz); nbo isrcache starts it. One per app (<app>-isr) on Kubernetes and Cloud Run, when the build has ISR pages (none on Lambda: served uncached)
@nbo/conformance, @nbo/loadtest HTTP-transcript conformance runner; load generator for the zero-failure switch test. Your shell / CI

NBO has no web interface of its own. You drive it with nbo-server, the HTTP API and the Terraform provider. A hosted dashboard, made separately by NBO's licensor, can sit on top of the same API; nothing in NBO needs it.

Edge & traffic

      

        Every project has one address on the NBO edge, http://<name>.127.0.0.1.sslip.io:9443. The edge picks a backend by weight and keeps each visitor on it (a random-id cookie, nbo_v, plus weighted rendezvous hashing in
        packages/edge/src/sticky.ts), so switching clouds is a dial, not a cutover, and a visitor never flips between clouds mid-session. (It does not cover a rolling update inside one cloud, where old and new copies briefly answer together.)
      

    


    

      

        Run a transfer
        

          A transfer sets up the other cloud, deploys the current production commit there, then shifts traffic in four steps. Each step is pushed to the edge before the next; you
          can stop at any step.

Idle. The real step delay is 20 s (transferConfig.stepDelayMs); this demo uses 1.2 s.

      

      

        Who owns the split
        

          The control-plane is the source of truth. Each cloud row stores traffic_weight; edge/edge-sync.ts turns them into the edge's target for the
          project's host.
        

        

          The edge keeps targets only in memory. When it restarts it forgets them, so the poll loop (every 45 s) runs reconcile(): for each project it reads
          GET /targets/<host> and re-sends the split if it differs. GET /projects/{id}/traffic answers edgeInSync: false for a split the edge doesn't have.
        

        

          In production the edge runs in a cluster instead (namespace nbo-edge, 2 pods behind a LoadBalancer, kept apart from nbo-system where NBO's own token lives). It reads its route table from the ConfigMap nbo-edge-routes, which the control-plane rebuilds from the database every 45 s and on every change; PUT /targets is off there. Certificates are Let's Encrypt (HTTP-01 through the edge, renewal under 30 days left, backoff 1 h / 6 h / 24 h) issued by the control-plane and stored as Secrets in nbo-edge; sites keep serving if NBO is down. Other clusters are reached through a relay (nbo-relay, pinned private CA, token), enabled per cluster with nbo-server cluster relay <id> --confirm-billing; transfers to a cluster without it are refused. Speed Insights is drained through the API server's pod proxy (token in the URL, may appear in audit logs; NBO's NetworkPolicy opens port 9444, which is not on the LoadBalancer). The cluster edge sets X-Forwarded-Proto from the listener and X-Forwarded-For from the connection's address, and ignores what the visitor sent in those, X-Real-IP and Forwarded. See the manual's Domains and the public edge chapter (docs/manual/domains.md).
        

        

          Two edges, one contract. The edge exists twice: the Node edge (packages/edge) and the Rust edge (packages/edge-rs, ADR 0005), with the same modes, ports, environment variables, admin API, route table and headers. A black-box suite (packages/edge/src/__tests__/blackbox) runs against whichever binary NBO_EDGE_BIN names, and both pass it. The Node edge stays the default until the last gate step holds: the Rust edge serving a site over HTTPS on a real cluster. To try it locally, run cargo build --release in packages/edge-rs and start target/release/nbo-edge instead of node packages/edge/dist/main.js. In production, set NBO_EDGE_IMPL=rust and run nbo-server edge reinstall; unset it and reinstall to go back. Two differences are on purpose: a compressed answer passes through as the backend sent it (only a page that gets the Speed Insights tag is decompressed), and the HTTPS listener offers HTTP/2 by ALPN, which NBO_EDGE_HTTP2=off turns off. Measurements are in ADR 0005.
        

        

          The first successful deploy of a project registers its host at 100% automatically. A backend on *.sslip.io (the local cluster's self-signed TLS) is sent with
          insecureSkipVerify: true; Cloud Run's *.run.app keeps normal verification.
        

        
PUT http://127.0.0.1:9444/targets/storefront.127.0.0.1.sslip.io
{ "backends": [
  { "url": "https://p0896d60b-k8s.127.0.0.1.sslip.io", "weight": 90, "insecureSkipVerify": true },

Routing & runtime

      
Inside every app container, nbo serve answers requests from the .nbo/ tree: one router, the same on every cloud.

    

    

      routes.json: six phases, in order. Select one.
      

      

    

    
What a request goes through

    

      

        Edge → app container
        

          The edge picks a backend, proxies the request and forwards it. The app server (nbo serve, inside every app image) sets
          x-nbo-deployment-id (the content id of the build that answered) on every response, because during a rollout only the answering pod knows its build. The edge
          removes no x-nbo-* header from responses, so visitors can see the content id; Speed Insights reads it to credit the right build.
        

        
The app image's entry point is node dist/main.js serve /app/app --port 8080: the CLI's own server over the baked-in .nbo/.

      

      

        App → functions
        

          Functions (SSR, middleware) run in their own containers. The app reads their URLs from /functions.json, written into the image at build time:
          http://<app>-fn-<name>:8080 on Kubernetes (a name over 63 characters becomes its first 54, a dash and 8 hex of its sha256,
          kubeName), the private *.run.app URL on Cloud Run, the function URL (auth AWS_IAM) on Lambda. On Cloud Run, @nbo/funcproxy fetches an ID token from the metadata server for
          each call; on Lambda (AWS_LAMBDA_FUNCTION_NAME set) it signs each call with SigV4 from the role's credentials and waits up to 15 s for the first byte.
        

      

      

        ISR and prerender
        

          Prerendered routes are served from cache and re-rendered after expiration. The cache is @nbo/isrcache, an in-memory service with a byte limit
          (96 MiB, least recently used first). A deploy runs one per app (<app>-isr: a Deployment and Service with a NetworkPolicy on Kubernetes, a private
          one-instance service on Cloud Run) and puts its address in the app's function URLs under __isrcache; nbo serve by hand uses
          NBO_ISRCACHE_URL. Cache keys start with the content id, so a new build never reads an old build's pages, and a cache read that fails or takes over 2 seconds is a miss.
          Each environment has one sealed revalidation secret (stage_revalidate_tokens), delivered at runtime as NBO_PRERENDER_BYPASS like any secret variable.
          POST /_nbo/revalidate through the edge goes to every backend of the host (204, the shared status, or 502 with a per-backend list); the control-plane routes
          .../stages/{id}/revalidate (also nbo-server revalidate) and .../revalidate-secret[/rotate] do the same from the API.
        

      

      

        Crons
        

          The control-plane's scheduler ticks, finds due crons (stored per cloud), and calls the cloud's live URL with
          Authorization: Bearer <HMAC-SHA256>, X-Nbo-Cron and X-Nbo-Cron-Timestamp. Crons run only in one cloud
          (cronsEnabled); a finished transfer moves the flag.

API reference

      

        Every route of the control-plane (127.0.0.1:8081) and the edge admin API (127.0.0.1:9444). Bodies are JSON; errors are
        {"error": "…"} with the real message. Access is read from packages/controlplane/src/http/access.ts:
        token takes an API token from anywhere, or no token from this computer; local takes no token, from this computer only (a token gets
        403 API tokens can't use this route): every /system/* route and the two legacy routes; webhook is checked by its signature;
        public needs nothing. pnpm docs:check fails when a route has no row here, a row has no route, or the access differs.

The link

      

        A hosted dashboard can drive a core over one connection the core opens itself (a WebSocket, or HTTPS long-poll). Each message is an
        instruction: an envelope naming one route of this API, with an id, a sequence number, a nonce and an expiry (60 seconds), signed by the dashboard's
        pinned key. Core verifies it (signature, expiry, a 64-wide replay window kept in the journal, then the route's tier from routeLinkTier in
        http/access.ts), opens any sealed field with its own key, calls the same handler the HTTP API uses, filters the answer so no secret leaves, and writes the journal row.
        Tier 0 reads, Tier 1 operates, Tier 2 changes what runs and also needs a signature from a member key (Admin or Owner). A build, deploy or transfer is Tier 1 unless its body has a values key (supplied variable values, names-only servers): then it is Tier 2 (suppliedValuesTier). Creating an environment is Tier 1 only for an ephemeral one (stageCreateTier); adding a domain and installing a certificate are Tier 2. Nothing in a deploy, poll, certificate, cron or
        expiry path waits on the link. The routes are in the table above under "The link to a hosted dashboard"; the manual chapter is docs/manual/link.md
        and the decision record is docs/adr/0008-the-link.md.
      

    

    

      Git: credentials, two ways to see a push
      

        Credentials. Each project reaches its repository with a credential of its own (src/git/git-credentials.ts, table
        project_git_credentials): public (none), token (an https:// address; the token goes to git steps only through
        GIT_CONFIG_COUNT, GIT_CONFIG_KEY_n and GIT_CONFIG_VALUE_n, never in the URL, and is added to the build's redaction list) or
        deploy-key (an ssh:// or git@host:path address; NBO makes the key pair and keeps the private half sealed). Tokens and private keys are
        sealed with the secret key; GET /projects/{id}/git shows only { kind, publicKey?, username? }. A credential stays with its host: moving a
        project's repository to another host needs the credential sent again with the move. Authenticated git steps never follow redirects.
      

      

        The deploy key flow. POST /projects/setup with credential: { kind: "deploy-key" } makes the key pair before the project's first
        look at the repository. That first git ls-remote fails until the public half is added to the repository as a read-only deploy key, so the project waits in
        needs-setup. nbo-server project setup prints the public half and the retry command; after the key is added,
        nbo-server project retry <id> (POST /projects/{id}/setup/retry) carries on. Terraform's nbo_project exposes the public half as the
        computed deploy_key_public. POST /projects/{id}/git/deploy-key replaces the pair.
      

      

        Host keys. github.com, gitlab.com and bitbucket.org are checked against the host keys they publish, which NBO carries in
        src/git/git-host-keys.ts and writes to known_hosts.published next to the database. Any other host is remembered in known_hosts
        the first time NBO reaches it and refused if its key changes.
      

      

        Seeing a push. The poller asks every project's repository for its branch heads every 45 seconds (git ls-remote), which needs nothing
        else. The per-project webhook (POST /projects/{id}/webhooks/github, HMAC-checked) is faster when GitHub can reach NBO. Both go through
        advanceHead, a compare-and-set on the head (the push's before), so a commit builds once and a replayed delivery builds nothing. A database from an older NBO that had its own GitHub App keeps building those
        projects with a token NBO asks GitHub for (src/git/github-legacy.ts) until they get a credential of their own.
      

    

    

      Access: tokens and the loopback rule
      

        NBO has no sign-in, members or roles. guardRequest (packages/controlplane/src/http/api-tokens.ts) runs once per request in
        createMux (http/handlers.ts), after router.match found the route, and reads that route's row in http/access.ts:
      

      
    
        
  • public (only GET /healthz): allowed from any Host, no token.
    • 
        
  • webhook: no token is read; the handler checks the signature. From loopback or the public address.
    • 
        
  • token: a valid Bearer nbo_… token from anywhere, or no header from loopback.
    • 
        
  • local: no header, from loopback only. A valid token gets 403.
    • 
      

      

        An Authorization header that isn't a valid token is 401, even on loopback. No header from a non-loopback Host, or with a
        cross-site Origin, is refused. A test fails when router.routes() and the table differ, a missing row is refused, and the level comes from
        the pattern the router matched, so odd spellings of a path can't pick a weaker rule. A token made by an older NBO for a Viewer or Developer (while it had sign-in)
        is refused with 401, because NBO can no longer limit it.
      

      

        Public address. NBO_PUBLIC_URL (https, no path, or the control-plane won't start) is the one non-loopback Host accepted, and only
        for requests with a token, the webhooks and /healthz; anything else for that host is 403. compose.public.yaml adds
        caddy:2.8.4 on 80 and 443, proxying to nbo:8081; NBO's own port stays on 127.0.0.1. The no-token rule trusts the
        Host header, so it is safe only while that port binds to loopback.

Terraform & API tokens

      

        Projects, variables, builds, domains and traffic can live in .tf files. The provider (packages/terraform-provider, Go, ADR 0004) is a separate
        program Terraform starts; it only talks to the control-plane's HTTP API, with an API token. Its unit tests run against a fake NBO. The acceptance test TestAccProject passed with Terraform 1.17.1
        against a local dev-mode NBO (2026-11-08): project, variable, deployment, data source, import and destroy. Domains and traffic haven't run through Terraform yet. The manual's Terraform chapter (docs/manual/terraform.md) is the user guide.
      

    


    

      

        How a request gets in
        
terraform apply
  └─ terraform-provider-nbo  (Go, plugin protocol 6)
       └─ HTTP  Authorization: Bearer nbo_…
            └─ ssh -L 8081:127.0.0.1:8081  (the only supported path)
                 └─ control-plane: guardRequest → router

        

          guardRequest (packages/controlplane/src/http/api-tokens.ts) runs before the handler. The API has no path prefix: an endpoint is
          http://localhost:8081, not an older NBO's /api/controlplane.
        

        
    
          
  1. An Authorization header that isn't a valid Bearer nbo_… token: 401, even on loopback.
    2. 
          
  2. A valid token on a local route (every /system/* route and the legacy /environments/{id}/deployments and /projects/{id}/environments): 403.
    3. 
          
  3. A valid token anywhere else: allowed, whatever the Host and Origin. Responses leave out the webhook signing secret.
    4. 
          
  4. No header: the loopback rule (a missing or non-loopback Host, or a cross-site Origin, refused).
    5. 
        

        
Webhook routes skip 1 to 3: their signature is the authentication. GET /healthz needs nothing.

      

      

        Tokens
        

          Made on the server with nbo-server token create <name> (POST /system/api-tokens, local only). A token is nbo_ plus 32 random bytes in hex, shown once. Table api_tokens keeps id (tok_…),
          a unique name, an 8-character prefix, the sha256 hash, created_at and last_used_at (written at most once a
          minute). Deleting the row revokes it at once.
        

        

          A token controls every site. It can't read stored cloud credentials, and in container mode (the production default) the builds it starts can't read NBO's files, environment or Docker socket or run code in NBO's process either, though they reach the network, including the cloud metadata address (which hands out the VM's own credentials on Google Cloud and AWS unless the host blocks it); but it can change variables, repositories and build commands, deploy any build and move traffic. With NBO_BUILD_ISOLATION=none builds run as the NBO user, so a token equals root on the server. A token has no expiry. The user_id and role columns are
          what an older NBO with sign-in wrote; NBO writes '' and admin.
        

        

          Don't expose the API through a VPN or reverse proxy. Requests without a token are trusted by their Host header, which a proxy can rewrite.
          The one exception is NBO's own public address: see the Access part of the API chapter and compose.public.yaml.

      Known limits
      
    
        
  • A commit landing right after setup can build once before the variables exist; nbo_deployment then builds again with them.
    • 
        
  • Changes to secret variables made through the API aren't noticed by Terraform.
    • 
        
  • A Cloud Run mapped domain has no records until ownership is verified, so its DNS record needs a second run.
    • 
        
  • Not on the Terraform Registry; the plugins-folder install, nbo_domain, nbo_traffic and the Cloudflare example are untried. The acceptance test serves the provider in-process.
    • 
        
  • The provider copies the API's shapes by hand: a changed route needs a matching change in packages/terraform-provider/internal/client, and PUT /projects/{id}/git replaces the whole config.
