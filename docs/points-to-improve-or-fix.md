(new, observed while verifying Task 9) On Windows, hard-killing `nbo serve` (Task Manager, `Stop-Process -Force`, or a script whose own kill doesn't reach it cleanly) leaves its spawned `funcproxy.NewLocalSpawner` child (the generic Node host) running, holding the function's bundle directory open, a later `nbo serve`/build on the same `.nbo/` dir then fails with `EBUSY`/`resource busy`, and the orphan keeps squatting whatever port it was given. `internal/funcproxy.NewLocalSpawner`'s `cleanup()` is correct and does run on a normal Ctrl+C (`os.Interrupt`) exit; the gap is that Windows has no real `SIGTERM` for `cmd/nbo/main.go`'s `signal.Notify(..., syscall.SIGTERM)` to catch, so anything that kills the process more forcefully than Ctrl+C bypasses it entirely. Not a Slice 2 blocker, Kubernetes deploys never use `NewLocalSpawner` (functions run as their own Deployment, per Task 8), but worth a real fix later (Windows Job Objects with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, or an equivalent process-group approach, so an orphan can't outlive its parent regardless of how the parent dies).
5. ~~A deployed Cloud Run app hangs forever, 401s, or 404s calling its own SSR function right after a fresh deploy~~ Fixed, four real bugs found running `scripts/verify-slice3-cloudrun.sh` against a real Google Cloud project across many real deploy cycles, none reachable from a unit test against fakes:
   - **Infinite hang.** `internal/funcproxy.MetadataServerIdentityToken` fetched the app's identity token via `http.DefaultClient` (no `Timeout`), and `cachedToken.get` holds a mutex for the whole fetch, so one slow/unreachable metadata-server call hung forever and serialized every other concurrent request to the same function behind it. Fixed in `4044f8d`: gave the metadata-server call its own 5s-timeout `http.Client`, and switched the base URL from the `metadata.google.internal` hostname to the `169.254.169.254` IP (matching Google's own Go metadata client's default).
   - **The real root cause, wrong Host header.** `httputil.NewSingleHostReverseProxy`'s default Director rewrites `req.URL.Host` but deliberately leaves `req.Host` (the actual Host header sent on the wire) as the original caller's, harmless for Kubernetes' in-cluster Service DNS, which routes by IP:port and ignores Host, but Cloud Run's shared `*.run.app` edge routes by Host/SNI. The proxied request to the function kept carrying the app's own external hostname, so Cloud Run's edge had no matching route and returned a clean, fast 404, never once reaching the function's own IAM check or handler, confirmed via diagnostic logging (`b4ceb16`) showing the function's logs never saw a real Bearer-token request across any run. Every other symptom (401s, 502s, timeouts, "no available instance" 429 storms from code reacting to a problem that wasn't there) traced back to this single bug. Fixed in `2c8d13a`: sets `req.Host = target.Host` before forwarding.
   - **Idempotency always redeployed.** Once the 404 bug was fixed and a real request finally succeeded, the *second* identical deploy still rebuilt everything instead of no-opping. `adapters/cloudrun.ContentIDLabel` truncates a content id to 32 hex chars to fit GCP's 63-char label limit, but `internal/deploy.Deploy`'s no-op check compared that truncated label against the full `sha256:...` id via plain `==`, which can never match. Fixed in `779e753`: added an optional `IDsMatch` comparator to `Deployer` (Kubernetes' annotation storage holds the full id, so its wiring is unaffected) and wired Cloud Run's to truncate both sides the same way before comparing.
   - **Retry tuning, now a secondary safety net, not the fix.** The 401/403-retry-with-backoff added in `75eab80`/`31ced58` and the verify script's own patient readiness probing (`3c7cdac` onward) were built chasing what looked like an IAM-propagation delay, real symptoms, wrong theory. They're kept as reasonable defensive behavior for the genuine (much smaller) propagation window, but the actual blocker the whole time was the Host header bug above.

   Net effect: a real first-time `nbo deploy --target cloudrun` now serves the app's own function calls immediately, and a second deploy of unchanged content correctly no-ops.

7. ~~A function whose own handler re-forwards a request's headers/body into its own outgoing `fetch()` call (exactly `entry-shim.mjs`'s own pattern) throws `InvalidArgumentError: invalid transfer-encoding header` the first time that request carries a real streamed body~~ Fixed: `packages/funcproxy/src/host.mjs` built the `Request` object it hands to a spawned function from the raw incoming HTTP request's own headers with no filtering at all (`Object.entries(req.headers)`), unlike `proxy.ts`'s own `proxyRequest`, which already excludes hop-by-hop headers (`HOP_BY_HOP_HEADERS`) on its own outgoing hop. 9. (new, from the 2026-11-04 PPR review and its fix round) Left open on purpose:
   - **HTML-limited bots get the shell (open).** For bots such as Bingbot and Slackbot Next bypasses the shell, because blocking metadata resolved during a resume lands after `</head>`. NBO doesn't: `prerender.ts` has no bot list. Checked on a real build with a Bingbot user agent: one whole document with the hole, so the page itself is fine. What's lost is dynamic metadata in the head, which the fixture doesn't have, so that part wasn't run. The fix is small but crosses packages: the adapter writes `htmlLimitedBots` into `x-nbo-ppr` (a schema change, and it must be RE2), and such a request takes `renderForOneVisitor`, which works for this already.
   - **Next's own draft cookie (open).** `draftMode().enable()` sets `__prerender_bypass`, which NBO doesn't read, so that visitor gets the build's shell with a hole rendered in draft mode: static parts don't show draft content. On an ISR page the cache answers as usual. `__nbo_bypass` does skip the shell and the cache, but on its own it doesn't turn on `draftMode()` in the app (real build: `draft:false`; with both cookies, `draft:true`).
   - **`next.config` `rewrites()` are ignored (open).** The adapter translates middleware only: rewrites written in `next.config.ts` never reach `routes.json`, and the build doesn't say so. Found building the rewrite check for ppr-app, which uses `proxy.ts` for that reason.
   - ~~**`s-maxage` reaches visitors.**~~ Settled by the Behind Cloudflare design: minimal mode's `cache-control: s-maxage=…` still reaches visitors, but Cloudflare's defaults don't cache HTML or JSON and respect `private` and `no-store`, which NBO sends on RSC and PPR responses. A Cache Everything rule, or one that ignores origin headers, is not supported.
   - **`/x.rsc` seeds are `application/octet-stream`.** Next's client doesn't ask for them with `partialPrefetching` off, so nothing reads them yet.
   - **Function trust (open).** The function trusts `next-resume` from anyone who can reach it; NetworkPolicy (needs a CNI that enforces it; dev kind has none) and Cloud Run IAM are the only defence.
   - **`x-invocation-id` memory.** A unique id per request means Next keeps up to 150 finished renders per route module that it can never reuse. Bounded.
   - **`previewModeId` in request headers.** `entry-shim.mjs` puts it in `x-prerender-revalidate`, so an app that logs or echoes `headers()` leaks the draft secret.
   - **Next's `revalidatePath()`/`revalidateTag()` don't reach the ISR cache (open).** Found proving a server action in real Chrome: the action's answer has the new render and `x-action-revalidated: 1`, but the next document `GET` of an ISR page is the old cached entry until its window ends (900 s on `/action-form`). Only `POST /_nbo/revalidate` clears that cache. Next doesn't name what it revalidated in the response, so fixing it needs a cache handler in the function, or at least dropping the page's own entry when a `POST` answers `x-action-revalidated`.
   - **RSC requests on ISR and hole-less pages aren't cached (open).** Every RSC prefetch or client-side navigation to an ISR or hole-less page is a full render in the function: `prerender.ts` sends them past the cache so flight data and HTML can't swap places. A page with many `<Link>`s to such pages costs one render per link in view, per visitor. Ideas, none built: store flight data in the ISR cache under its own key (the path plus an rsc marker), with the same fresh/stale/expired rules and the same invalidation as the page; answer a static prefetch from the `/x.rsc` seed the build already writes (see the seeds item below); share one in-flight render between identical requests. `docs/production.md` tells site authors to use `prefetch={false}` until then.

   - **The fixtures print the time on purpose.** `fixtures/next-app/app/isr-demo/page.tsx`, `fixtures/ppr-app/app/action-form/page.tsx` and `fixtures/ppr-app/app/cache-life/page.tsx` render `Date.now()`, and Next prerenders them at build time, so `/isr-demo`, `/action-form`, `/cache-life` and their `.rsc` files differ on every build. 17. (new, found while writing spec 1.0, 2026-11-09)
   - **Production ISR (done 2026-11-09; what stays open).** Deploys run one cache per app and give each environment a revalidation secret; the edge fans revalidation out to every cloud. Open: the cache is in memory only (no persistent cache; a restart renders pages again on demand); on Cloud Run, request-based CPU slows a background render between requests; a cache that Cloud Run stopped when idle starts cold after about a second; the conformance transcripts for a cached page and a revalidation with the generated secret can't hold a per-deploy secret or a timestamped body, so those two exchanges stay serve tests (the fan-out exchange is a platform transcript); not tried on a real cluster or Google project.
   - **Middleware response headers named `x-nbo-*` reach the visitor (open, small).** The router strips only `x-nbo-next`, `x-nbo-rewrite`, `x-nbo-request-headers` and `x-nbo-request-header-*`; any other `x-nbo-*` header a middleware sets is merged into the final response (the app server then replaces `x-nbo-deployment-id`). The spec states this. Decide whether to strip every reserved `x-nbo-*` name except `x-nbo-deployment-id` and `x-nbo-carried-from`; that would be a router change with a transcript, and a minor release if the spec changes.
