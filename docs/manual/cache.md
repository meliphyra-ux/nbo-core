# Page cache and revalidation

Some pages in a Next.js site are built once and then kept for a while, so visitors get them quickly without your code running each time. This chapter explains what NBO does with such pages, how to make them fresh at once, and what to check when that fails. If your site is a React single-page app or a static site, nothing here applies to you.

## Which pages are cached

In Next.js this feature is called ISR (incremental static regeneration). A page is ISR when its code says how long it may be kept, for example:

```ts
// app/blog/page.tsx
export const revalidate = 60; // keep this page for 60 seconds
```

Next.js writes such a page ahead of time at build, serves that copy, and after the time is up renders a new copy in the background. A visitor is never made to wait for the new render: they get the old copy ("stale") while the new one is made.

NBO does the same on every cloud. When your build contains at least one such page, NBO starts a small page cache next to your app, with nothing for you to set up. Pages that your code marks as never cached, and pages that depend on the visitor (cookies, for instance), are not stored.

What gets stored:

- Pages (`GET` and `HEAD`) answered with `200`, a redirect (`301`, `302`, `307`, `308`) or "not found" (`404`, `410`). A `5xx` error is never stored, and a failed background render keeps the old copy.
- Not the data your code fetches. Next.js's own data cache (`fetch` results, `unstable_cache`) is not part of what NBO deploys.

A new build never shows an old build's pages. Every stored page is filed under the build's content id (see [Builds](./builds.md)), so a new version starts with an empty cache. A redeploy of the same build, for instance after changing a variable, keeps its stored pages.

If the cache is slow or gone, your site still works. A cache that does not answer within 2 seconds counts as "not stored yet", and the page is rendered. Saving a page happens after the visitor has their answer.

## Revalidate from your code

To refresh pages before their time is up, send a request to your own site:

```bash
curl -X POST https://your-site.example/_nbo/revalidate \
  -H "Authorization: Bearer $NBO_REVALIDATE_SECRET" \
  -H "content-type: application/json" \
  -d '{"tags":["posts"],"paths":["/blog"]}'
```

- **paths** are page addresses starting with `/`. **tags** are names your code attached to its data (`fetch(url, { next: { tags: ["posts"] } })`). Send either or both, at most 256 of each.
- The stored copy is dropped at once. The next visit renders the page again (that visitor waits for the render) and stores the result for the ones after.
- The secret is generated by NBO. Your app and functions can read it as the variable `NBO_PRERENDER_BYPASS`, so an admin route of your own can call the address above with `process.env.NBO_PRERENDER_BYPASS`.

`revalidatePath()` and `revalidateTag()` inside a Next.js server action do not clear NBO's cache yet. The person who ran the action sees the new page, but a reload shows the stored copy until its time is up. Call `/_nbo/revalidate` as above when it must be at once.

## Revalidate from a CMS

A CMS (Contentful, Sanity, WordPress and so on) can call a webhook when someone publishes. Point it at the same address, through your site:

1. Read the environment's secret (see [The revalidation secret](#the-revalidation-secret) below).
2. In the CMS, add a webhook to `https://your-site.example/_nbo/revalidate`, method `POST`, with the header `Authorization: Bearer <the secret>` and a JSON body such as `{"paths":["/blog"]}`.
3. Publish something, then load the page twice.

Use your site's address, not NBO's own address. NBO's API stays behind your SSH tunnel; a CMS cannot reach it, and does not need to. If your CMS can only send a fixed body, put one path or tag in it. If it cannot set headers, point it at a small function of your own that holds the secret and makes the call.

## Revalidate through NBO

NBO can make the call for you. Each environment (Production, one of your own, or a running ephemeral environment) has its own cache and its own secret; `GET /projects/{id}/stages` lists their ids.

- **Revalidate pages:** `POST /projects/{id}/stages/{stageId}/revalidate` with `{"tags": [...], "paths": [...]}` (at least one), or on the server `nbo-server revalidate <projectId> --stage <stageId> --path /blog --tag posts`. The answer is per cloud, such as "Cloud Run answered 401" or "revalidated". NBO calls your site's own address for you. In production mode it refuses to do that over plain `http`, so the secret never crosses the internet unprotected; wait until the address is `https`.
- If the environment has no ISR page, the call answers `409` "Nothing in this environment uses ISR yet".

## The revalidation secret

`POST /projects/{id}/stages/{stageId}/revalidate-secret` answers the environment's secret, making it on first use. It works with an API token, so treat that token like the secret itself.

### Rotating the secret

`POST /projects/{id}/stages/{stageId}/revalidate-secret/rotate` makes a new secret and answers it. Each cloud picks it up on its next deploy, so start a build after rotating (`POST /projects/{id}/builds`, with `stage` for an environment other than Production). An ephemeral environment starts using the new secret on the next push to its branch. Until a cloud has deployed, its old secret still works; after that, only the new one does. Update the secret in your CMS and anywhere else it is stored.

## One cache per environment and cloud

The cache belongs to one app: one environment on one cloud.

|                                                                      | Cache                    | Secret       | A revalidation reaches |
| -------------------------------------------------------------------- | ------------------------ | ------------ | ---------------------- |
| Production on two clouds                                             | one per cloud            | Production's | both                   |
| A custom environment such as `staging`                               | one per cloud it runs on | its own      | its own clouds         |
| An [ephemeral environment](./environments.md#ephemeral-environments) | one, on its cloud        | its own      | that cloud             |

- An ephemeral environment or `staging` can never write into Production's cache, and its secret cannot refresh Production.
- When a site is on several clouds, NBO's edge sends your request to every cloud that serves the address, clouds at 0% traffic included, because each has its own cache. It answers `204` when all said yes. If they all gave the same answer, you get that answer (a wrong secret is a plain `401`). Otherwise you get `502` with a list of which cloud failed, by environment id (`null` for a cloud the edge has no id for).
- Upgrade the edge first (`nbo-server edge reinstall`). An older edge reaches only one cloud.
- Without an edge (production mode with only Cloud Run), NBO's revalidate route calls each Cloud Run address itself. A cluster app has no public address without the edge, so it cannot be revalidated that way.

## What it costs

- **Kubernetes** adds one small pod per app that has ISR pages (10m CPU and 64 MiB asked for, 256 MiB at most). No separate bill.
- **Cloud Run** adds one service per app, billed only while it answers: about $3 or less a month at a million ISR page views, nothing while idle, mostly inside Cloud Run's free tier. Add about $0.06 a month for the secret and about $0.02 for the cache image in Artifact Registry.
- A build with no ISR page gets no cache, and the next deploy removes the one an earlier build had.

## Limits

- **In memory only.** The cache holds up to 96 MiB and drops the pages used least recently first. A page larger than a quarter of that is not stored. A restarted cache starts empty, and pages render again on the next visit.
- **Cloud Run sleeps.** The cache service stops when the site is idle and wakes in about a second, so a quiet site loses its stored pages. The work behind a stale page runs after the answer is sent, and Cloud Run gives a service little CPU between requests, so the background render can be slow.
- **Kubernetes policy.** The cache runs as user 1000 with a read-only root filesystem and no extra permissions. A cluster policy that forces another user or forbids that will stop it from starting.
- **Not shared.** Clouds and environments do not share a cache, and there is no "purge everything" call. Revalidate by tag or path.
- **Prefetching.** A page with many `<Link>`s to ISR pages costs one render per prefetch, because those requests skip the cache. Use `prefetch={false}` where it matters.
- **Partial prerendering** shells do not refresh until the next deploy, even for `"use cache"` content.

## If it does not work

| What you see                                             | What it means                                                                                                                                                                                                                                                                | What to do                                                                                                    |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `409`: "Nothing in this environment uses ISR yet"        | The environment has never had a build with ISR pages, so there is no secret.                                                                                                                                                                                                 | Deploy a build that has a page with `revalidate`, then try again.                                             |
| `409`: "certificate isn't active yet"                    | The address is not `https` yet, and NBO will not send the secret over plain `http`.                                                                                                                                                                                          | Wait for the certificate (see [Domains](./domains.md)), then try again.                                       |
| `409`: "has no address" or "nothing ... is deployed yet" | There is nowhere to send the call yet.                                                                                                                                                                                                                                       | Finish a first deploy.                                                                                        |
| `401`                                                    | The secret is wrong, or that cloud has not deployed since you rotated it.                                                                                                                                                                                                    | Read the secret again. After a rotation, deploy that environment again.                                       |
| `400`                                                    | The body is not `{"tags": [...]}` or `{"paths": [...]}`.                                                                                                                                                                                                                     | Send only those fields; paths start with `/`.                                                                 |
| `502` with a list                                        | Some clouds failed. The list names which. `unreachable or timed out` means no answer in 10 seconds.                                                                                                                                                                          | Check that cloud (`GET /projects/{id}/summary`), then try again.                                              |
| `413`                                                    | The body is over 64 KiB; the edge refuses it.                                                                                                                                                                                                                                | Send fewer tags and paths per call.                                                                           |
| `500`: "no ISR cache service configured"                 | The live build has no ISR page, so no cache was started.                                                                                                                                                                                                                     | Deploy a build that has one.                                                                                  |
| The old page still shows                                 | Revalidation removes NBO's copy, so the cause is usually elsewhere: a browser or CDN (Cloudflare, for example) cache in front of NBO; the call went to a different address or environment than the page you are looking at; or the call answered `401` or `502` (see above). | Load the page with the browser cache off, check the address and environment, and read the answer of the call. |

No real cluster or Google project has served a cached page, so cost figures are estimates. [What has been tried for real](./tried.md) lists the rest.
